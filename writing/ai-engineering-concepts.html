Beyond the buzzwords: 7 AI engineering concepts and the questions that matter

November 2026 · 14 min read · AI engineering

RAG. Agents. LangGraph. MCP. Vector databases. Fine-tuning. Evaluation. These seven terms come up in almost every conversation about building AI systems today, and most people working in the field can give a quick definition of each.

But a definition is only the start. Real understanding shows in the follow-up questions. When would you use it, and when wouldn't you? How would you know it's working? What goes wrong in practice? Those are the questions that matter when you're building something people will rely on.

This guide covers all seven concepts in the same way: what each one is in plain English, a simple example, when to use it and when not to, the follow-up questions worth being able to answer, and a common mistake. We'll use one example throughout, so by the end you'll see how the pieces fit together.

Our example: an HR assistant

Imagine a company builds an AI assistant for its employees. It should be able to:

  • answer policy questions, like "How much parental leave do I get?"
  • check personal information, like "How many holiday days do I have left?"
  • take simple actions, like "Book Friday off for me."

Each of the seven concepts plays a part in building this assistant well.

1. RAG (retrieval-augmented generation)

What it is: a way to make a language model answer from your information. When a question comes in, the system first finds relevant pieces of your documents (retrieval), then gives them to the model to write an answer (generation).

In our example: for "How much parental leave do I get?", the assistant searches the HR policy documents, finds the parental leave policy, and answers from it, ideally with a link to the source.

Use it when answers depend on information the model wasn't trained on, or that changes often: internal policies, product documentation, recent data. Don't use it when the question needs live personal data (that's a tool call, see MCP below), or when a simple database lookup would do.

The follow-up questions:

  • "How would you improve its accuracy?" First work out where it's failing: is it finding the wrong documents, or finding the right ones and writing a bad answer? Then fix that step, for example with better chunking or reranking for retrieval, or clearer instructions for generation.
  • "How would you know it improved?" Test it on a fixed set of questions with known answers before and after the change, and compare the scores.
  • "What happens when the answer isn't in the documents?" It should say so clearly, not guess. This needs to be designed and tested.

Common mistake: judging RAG only by whether answers sound right. A fluent answer can still be built on the wrong document. I've written a full guide to this: Is your RAG system actually working?

2. Vector databases

What it is: a database built to search by meaning, not exact words. Each piece of text is turned into an embedding: a long list of numbers that represents its meaning, so that similar ideas end up close together. A vector database stores these embeddings and quickly finds the ones closest to a question.

In our example: an employee asks, "Can I take time off when my baby is born?" The policy is titled "Parental leave" and never uses the word "baby". Keyword search might miss it. Meaning-based search finds it, because the two ideas are close.

Use it when you need to search large amounts of text by meaning, which is the "retrieval" part of most RAG systems. You may not need a dedicated one when your document set is small, or your existing database or search engine already supports vector search. Many teams start with an extension to a database they already run and only move to a specialised product when scale demands it.

The follow-up questions:

  • "Do you really need a separate vector database?" Often not at first. The right answer depends on data size, speed needs, and what your team already knows how to run.
  • "How do you keep it up to date?" When a document changes or is deleted, its embeddings must be updated or removed too. Otherwise the assistant keeps answering from an old policy.
  • "Is meaning-based search always better?" No. It can miss exact terms like policy codes, names or numbers. Many systems combine it with keyword search, which is called hybrid search.
  • "Who's allowed to see what?" If some documents are restricted, the search must respect those permissions, not just return the closest match.

Common mistake: treating the vector database as the main design decision. In practice, how you split documents into chunks, which embedding model you use, and how you keep data fresh matter far more than which product you pick.

3. Fine-tuning

What it is: taking an existing model and training it further on your own examples, so a particular behaviour becomes part of the model. Modern approaches often train only a small set of extra parameters rather than the whole model, which makes fine-tuning much cheaper. LoRA is a well-known example of this.

In our example: the HR team receives thousands of requests and wants each one sorted into one of 30 internal categories, in a fixed format, every time. A small model fine-tuned on a few thousand past requests that people have already labelled can do this quickly, cheaply and consistently.

Use it when you need a consistent behaviour, style or format that prompting can't make reliable, or when a smaller specialised model would save real cost at high volume. Don't use it to teach the model facts that change, like this year's holiday policy. That's what RAG is for. A fine-tuned model can't tell you where its answer came from, and it goes out of date the moment the policy changes.

The follow-up questions:

  • "Why fine-tune instead of using RAG or a better prompt?" A simple rule: RAG for what the model needs to know, fine-tuning for how it needs to behave, and always try a good prompt first.
  • "How much data do you need?" Usually hundreds to a few thousand good examples for a focused task. Quality matters far more than quantity.
  • "How do you know it worked?" Test on examples the model never saw during training, and compare against the original model with a good prompt. Also check it hasn't got worse at things it used to do well.
  • "What does it cost to maintain?" Training data to keep current, retraining when needs change, and model versions to track. Fine-tuning is a commitment, not a one-off.

Common mistake: reaching for fine-tuning first because it feels more advanced. Most problems are solved more cheaply with better prompts or better retrieval. I go deeper on this choice in What actually matters when you design an agentic AI system.

4. Agents

What it is: a system where a language model doesn't just answer, but decides what to do next. It can choose which tools to use, look at the results, and take further steps until the task is done. The key difference from a normal chatbot is that the model controls part of the process.

In our example: "Book Friday off for me." The agent checks the employee's remaining holiday balance, checks the team calendar for conflicts, submits the request, and confirms. Several steps, decided by the agent, using different tools.

Use it when a task needs several steps, and the right next step depends on what was found in the previous one. Don't use it when the steps are always the same. A fixed workflow, where the model only does specific steps, is easier to test, more predictable and cheaper. Many systems described as "agents" work best as well-designed workflows with the model making decisions only where judgement is really needed.

The follow-up questions:

  • "Agent or workflow, and why?" Use the least freedom that solves the problem. Give the model more control only where it genuinely helps.
  • "What stops it from looping forever or spending too much?" Limits on steps, time and cost, and a clear way to stop and say "I couldn't complete this".
  • "What is it allowed to do without asking?" Reading information can often be automatic. Actions with real consequences, like submitting a request, may need the person to confirm.
  • "How do you test it?" Check both the final result and the steps it took. An agent can reach the right answer for the wrong reasons, and that will eventually fail.

Common mistake: making everything an agent. Autonomy makes systems harder to predict, test and explain. It should be used where it adds value, not by default.

5. LangGraph

What it is: an open-source framework for building agents and AI workflows as a graph. You define the steps as nodes, the possible paths between them as edges, and a shared state: the information that's passed along and updated as the work moves through the graph. Edges can be conditional, so the next step depends on what just happened. The graph can also loop back, pause for a person to approve something, and save its progress so it can resume later.

In our example: the holiday booking flow becomes a small graph: understand request → check balance → check calendar → (if there's a conflict, ask the employee) → submit → confirm. Each box is a node, and the "if there's a conflict" decision is a conditional edge.

Use it when your process has branches, loops, pauses for human approval, or needs to remember where it is across steps. Making the flow explicit as a graph makes it much easier to understand, test and debug than a free-running agent. Don't use it when your flow is a simple straight line. A few function calls are easier to read and maintain. It's also worth remembering that LangGraph is one framework among several. The underlying idea, making the flow explicit, matters more than the specific tool.

The follow-up questions:

  • "Why use a graph instead of letting the agent decide everything?" Because explicit paths are predictable and testable. You choose where the model has freedom and where it doesn't.
  • "What's in the state, and why?" Only what later steps need. A bloated state makes the system harder to follow and more expensive to run.
  • "What happens if a step fails halfway through?" With saved progress (checkpoints), the flow can retry or resume from the last good step instead of starting again, and without repeating actions like submitting a request twice.
  • "How do you test it?" Test each node on its own, then test the important paths through the graph, including the failure paths.

Common mistake: knowing the framework but not the design. Being able to write LangGraph code is less valuable than knowing which steps should be fixed, which should be left to the model, and where a person should be involved.

6. MCP (Model Context Protocol)

What it is: an open standard for connecting AI applications to tools and data. A common comparison is a USB port for AI: instead of building a custom connection for every combination of AI app and system, each system exposes its capabilities once through an MCP server, and any compatible AI app can use them. An MCP server can offer tools (actions, like "submit leave request"), resources (data, like "employee holiday balance") and prompts (reusable instructions).

In our example: the HR system gets an MCP server offering "get holiday balance", "get team calendar" and "submit leave request". The assistant uses them, and so could any other AI tool the company adopts later, without new integration work.

Use it when several AI applications or agents need the same tools, or you want a consistent, reusable way to connect AI to internal systems. It may be unnecessary when you have one simple integration used by one application. A direct function call is fine there.

The follow-up questions:

  • "How is MCP different from just calling an API?" Under the hood, an MCP server usually still calls your normal APIs. What MCP adds is a standard way for AI applications to discover available tools, understand what they do, and call them in the same way everywhere.
  • "How do you control what the AI is allowed to do?" Authentication, and least-privilege permissions: the assistant should only access what the employee it's helping can access. Every call should be logged, and high-impact actions should need approval.
  • "Can tool results be trusted?" Not blindly. Text returned by a tool, like a document or an email, could contain instructions trying to manipulate the AI. This is called prompt injection, and tool outputs should be treated as untrusted data.
  • "How do you change a tool without breaking things?" Clear descriptions and versioning, the same discipline as any API.

Common mistake: giving an agent broad access "to make it work". Convenience now becomes a security problem later.

7. Evaluation

What it is: measuring whether your AI system actually does what it should, reliably, and whether a change made it better or worse. It's the concept that connects all the others, because every one of them raises the same question: how do you know it's working?

In our example: before each release, the HR assistant is tested on a fixed set of real questions with known correct answers and known source documents. Retrieval is scored on whether it found the right policy. Answers are scored on whether they're correct and supported by the sources. Actions are tested on whether the right steps were taken, and whether the assistant asked for confirmation when it should. After launch, employee feedback and repeated questions show how it's doing in real life.

Use it: always. This is the one concept with no "when not to".

The follow-up questions:

  • "Which metrics would you track?" It depends on the part. For retrieval: Precision@K and Recall@K. For answers: correctness and faithfulness, meaning every claim is supported by the sources. For agents: task success, the steps taken, and errors. Plus latency and cost for everything.
  • "How would you build a test set?" Start with real questions, have experts record the correct answers and sources, and include hard cases and questions with no answer. Start with 50 to 100 and grow it from real failures.
  • "Offline or online?" Both. Offline testing on a fixed set before release; online monitoring of real use afterwards.
  • "Can an AI grade the AI?" Yes. It's called LLM-as-a-judge, and it's useful for scale, but only after checking its scores against human experts on the same answers.

Common mistake: treating evaluation as something to add at the end. It should come first. Without a way to measure, every other decision on this list is a guess. I've written more about this for RAG systems and for AI agents.

Seen this way, the seven terms aren't a list of buzzwords to collect. They're parts of one system, each chosen for a specific job.

The pattern behind every follow-up question

If you look back at the follow-up questions across all seven concepts, the same four keep appearing:

  1. When would you use it, and when wouldn't you?
  2. How would you know it's working?
  3. What can go wrong, and how would you handle it?
  4. What does it cost to build and to maintain?

Being able to answer these for any tool is what turns knowing the names of things into knowing how to build with them. And that's the real skill. New frameworks and terms will keep arriving, but these four questions will apply to every one of them.
