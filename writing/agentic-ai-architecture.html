What actually matters when you design an agentic AI system

November 2026 · 10 min read · Architecture

You can build an impressive AI agent demo in an afternoon. Give a model a few tools, write a good prompt, and it will happily search, reason and write something that looks smart. Building a system that people rely on every day is a different job, and it usually takes months.

Almost none of that difference comes from the model. It comes from architecture: how the work is structured, what the agent is allowed to touch, how you see what it's doing, and what happens when it gets something wrong.

These are the design decisions I think matter most, and the trade-offs behind each one.

The shape of a good agentic system

Before the details, here is the overall picture I design towards. The model sits in the middle, but most of the boxes around it are about control, visibility and trust.

1. Start with a workflow, and earn autonomy

"Agentic" covers a wide range. At one end is a fixed pipeline where an LLM does one step. At the other is a fully autonomous agent that decides its own plan, picks its own tools and keeps going until it thinks it's finished.

My default is to use the least autonomy that solves the problem. Most real tasks have a shape you already know: gather information, analyse it, produce something. Encoding that shape as an explicit workflow, for example as a graph of steps with clear transitions, makes the system easier to test, easier to debug and far more predictable. You then give the model freedom inside the steps where judgement actually helps.

Autonomy should be earned. When evaluation shows a step is reliable, you can loosen the structure around it. Going the other way, starting fully autonomous and trying to add control later, is much harder.

2. One agent or many?

Multi-agent systems are attractive, and they're often the right answer, but every extra agent adds coordination, latency and another place for things to go wrong. Debugging a conversation between five agents is not fun.

I split work into separate agents when there's a real reason:

  • the tasks need different tools or permissions,
  • they need very different context, and mixing it would confuse the model,
  • they can run in parallel and save real time,
  • or they need to be tested and improved independently.

If none of those apply, one well-designed agent is usually better. When there are several, the shared state between them should be explicit and visible, not hidden inside chat messages.

3. Tools are the real interface

An agent is only as good as the tools it can use. In my experience, a surprising number of "the model is wrong" problems turn out to be "the tool is confusing" problems.

Good tools are small and focused, with clear names, clear descriptions and predictable inputs and outputs. They return helpful error messages, because the model will read them and try again. Standards like the Model Context Protocol (MCP) make it much easier to connect agents to systems in a consistent way, and to reuse tools across agents.

Permissions belong here too. An agent should act with the least access it needs, ideally the same access as the person it's working for, and every tool call should be logged. If an agent can read or change something, you need to be able to say exactly why it was allowed to.

4. Use the right model for each step

Not every step needs your biggest model. Some steps are better handled by a simple rule, some by a classic machine learning model, some by a small fast LLM, and only some by a large reasoning model. Matching the model to the step makes the system cheaper, faster and often more accurate.

Where the models run is an architecture decision as well. Hosted APIs are fast to start with. Self-hosted or private deployments can make more sense when data is sensitive, when it must stay in a particular region, or when volumes are high enough that cost per call starts to dominate. I try to keep the model behind a clean interface so this decision can change later without rebuilding everything.

The model you use today will be replaced within a year. Good architecture makes that change boring.

5. Context is a design decision

What you put in front of the model matters as much as which model you use. More context isn't automatically better. Long, noisy context makes models slower, more expensive and easier to distract.

I treat context as something to design: retrieve only what's relevant, summarise long histories, and keep the instructions clear and stable. Wherever possible, I ask the agent to point to its sources, so a person can check each claim against the original data. That one habit makes systems far easier to trust and to debug.

6. RAG, fine-tuning, or neither?

This is one of the most common questions I get, and the simplest rule I know is this: use retrieval (RAG) for what the agent needs to know, and fine-tuning for how the agent needs to behave.

RAG means fetching relevant information at the moment the agent needs it and putting it into the context. Fine-tuning means further training a model on your own examples so that a behaviour becomes part of the model itself. They solve different problems, and mixing them up is expensive.

Take an IT support agent for a large company as an example.

  • Answering "How do I set up the VPN on my new laptop?" The answer lives in the help centre, and those articles change every few weeks. This is a RAG problem. Fine-tuning the answers into the model would make them out of date by the next release, and you couldn't show the user where the answer came from. With retrieval, you update the article and the agent knows straight away, and it can link to its source.
  • Sorting thousands of incoming tickets into the company's own 40 categories, in a fixed format, every time. This is about consistent behaviour, not changing knowledge. A large model with a long prompt can do it, but it's slow and costly at volume, and it drifts on edge cases. This is where fine-tuning a small model on a few thousand past tickets that people have labelled pays off: it becomes fast, cheap and very consistent at this one job.
  • Both together. The full agent uses the fine-tuned small model to route each ticket, and RAG to find the right help articles before drafting a reply. Each technique does the job it's best at.

Before either, I always try good prompting with a few examples. It's often enough, and it's by far the cheapest option to change. My usual order is: prompt first, add RAG when the agent needs knowledge it doesn't have, and fine-tune only when you need a behaviour that prompting can't make reliable, or when volume makes a smaller specialised model worth it. Fine-tuning also brings its own work: training data to maintain, evaluation to re-run and models to version. That cost should be a deliberate choice.

7. Put guardrails at the edges

Guardrails work best at the boundaries of the system:

  • On the way in: validate requests, and remove or mask personal data the model doesn't need.
  • From tools: treat anything a tool returns as untrusted. Text inside a document or web page can contain instructions, and an agent shouldn't follow them. This "prompt injection" risk is one of the most underrated problems in agent design.
  • On the way out: check that outputs follow the expected structure and don't contain things they shouldn't.
  • On actions: anything with real impact, like sending, changing or deleting, should be limited, and the important actions should need a person's approval.

8. Build observability in from day one, and design for failure

If you can't see what an agent did, you can't fix it. Every run should leave a trace: the steps taken, the tools called, the inputs and outputs, the time taken and the cost. These traces are what make debugging possible, and they're the foundation for evaluation. I've written separately about how to validate whether an agent is right.

Agents also fail in ways normal software doesn't. They loop, they time out, they get stuck on a bad tool result. So the design needs limits on steps, time and cost, sensible retries, fallbacks, and above all a graceful way to stop. An agent that says "I couldn't complete this, here's what I found" is far more useful than one that guesses.

9. Treat people as part of the architecture

Human oversight is often drawn as a box at the end. I think it belongs in the design from the start. Where does a person review, approve or correct? How does their feedback get captured and used? Can they easily override the agent? Is there an audit trail that shows who asked for what, what the agent saw, what it did and who approved it?

These questions shape the workflow, the user interface and the data model. Answer them early and the system feels trustworthy. Answer them late and you end up rebuilding.

A checklist for any agentic design

  • Is this the least autonomy that solves the problem?
  • Does each agent exist for a clear reason?
  • Are the tools small, clear and permission-limited, with every call logged?
  • Is each step using the simplest model that does the job well?
  • Can every important claim be traced back to a source?
  • Are we using RAG for knowledge and fine-tuning only for behaviour we can't get reliably any other way?
  • Are tool outputs treated as untrusted, and are high-impact actions approved by a person?
  • Can we trace every run, and are there limits on steps, time and cost?
  • Can we swap the model without redesigning the system?

None of this is as exciting as a new model release. But it's the difference between an agent that impresses people in a meeting and one they're still happy to rely on a year later. That's the part I enjoy most: designing systems that turn what AI can do into something people can depend on.
